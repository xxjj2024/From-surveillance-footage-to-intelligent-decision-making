# 从监控视频到智能判定：一个视觉识别系统的原理剖析

> 本文以一套实际运行的"废旧机动车拖带拆解零件检测"系统为例，深入剖析两个核心脚本
> `video_check.py` 与 `test_qwen_vl.py`。目标读者是对计算机视觉感兴趣的初学者——
> 我们不谈环境配置，只讲清楚**这些代码为什么这样写、每一行背后的识别原理是什么**。

---

## 一、项目总览：要解决什么问题，怎么解决

### 1.1 业务问题

在废旧机动车回收拆解场，有一类违规行为很难靠人工盯监控发现：**机动车拖带、悬挂、
装载着拆解后产生的零碎金属零件**（发动机残骸、车架碎片、轮毂等）在厂区内行驶。
这些零碎零件散落在车斗里或被绳子拖着，存在掉落伤人和物料流失的风险。

人工审核的困境在于：监控 7×24 小时运行，一天产生几十个小时的视频，
没有任何人能逐帧看完。

### 1.2 技术思路：把"看视频"拆解成机器擅长的两个子问题

这个系统的核心洞察是：**"找出哪辆车在拖零件"其实是一个复合问题**，
直接让一个模型端到端解决既困难又不可控。于是它被拆解成两级流水线：

```
┌─────────────────────── 第一级：找到"车" ───────────────────────┐
│  video_check.py                                                │
│  视频抽帧 → YOLO 目标检测（卡车）→ 裁剪出卡车区域图片            │
│  输入：几十小时的监控视频   输出：几百张"卡车照片"               │
└──────────────────────────┬────────────────────────────────────┘
                           ▼
┌─────────────────────── 第二级：判断"车上有什么" ────────────────┐
│  test_qwen_vl.py                                               │
│  卡车图片 → 视觉语言模型(VLM) → "是/否"判定 + 文字描述           │
│  输入：几百张卡车照片      输出：一份判定报告（CSV）             │
└────────────────────────────────────────────────────────────────┘
```

这个拆解体现了计算机视觉工程中一个极其重要的设计哲学——**"检测"与"理解"分层**：

- **第一级回答"在哪里"**（Where）：目标检测是成熟、快速、便宜的
  传统 CV 任务，YOLO 每张图推理只需几十毫秒；
- **第二级回答"是什么、在干什么"**（What & Doing）：这需要真正"理解"
  画面语义——分辨"一堆暗色金属碎块"和"一堆黑色轮胎"的区别，
  这类任务在五年前需要专门训练分类器，如今可以直接交给
  视觉语言模型（Vision-Language Model，VLM）用一句提示词完成。

分工的好处是**成本可控**：YOLO 处理海量视频帧几乎不花钱，
只有裁剪出来的几百张"疑似有用"的图片需要送进大模型做昂贵的语义推理。
这种"便宜模型广撒网、昂贵模型精判定"的漏斗结构，是当前工业界
视觉系统的主流架构。

### 1.3 两个脚本的协作方式

两个脚本是**解耦**的：`video_check.py` 把裁剪结果写入一个固定文件夹
（`卡车裁剪图/`），`test_qwen_vl.py` 从同一个文件夹读取。中间通过
**文件系统**交接，而不是内存直传。这带来三个工程好处：

1. **可中断**：任何一步跑一半都可以停，下次接着来；
2. **可人工介入**：中间产物（裁剪图）本身就是人眼可审查的，
   可以先人工筛一遍再送大模型，节省推理费用；
3. **可复用**：裁剪出的图片既是判定输入，也是日后训练自定义模型的
   宝贵素材。

## 二、详解 `video_check.py`：如何从海量视频中"淘金"

### 2.1 What——它在系统中的角色

`video_check.py` 是流水线的**第一级：目标检测与素材采集器**。
它的工作用一句话概括：

> 扫描指定目录下所有视频文件，每隔一秒抽取一帧，用 YOLO 模型找出
> 画面中的卡车，把卡车所在区域裁剪成图片保存下来。

它的输出不是结论，而是**中间产物**——一批以文件名自带溯源信息
（来源视频 + 出现时间 + 置信度）命名的卡车图片。命名规则
`{视频名}_t{秒数}s_{置信度}.jpg` 意味着任何一张图都能反查出
"它出现在哪个视频的第几秒"，这对后续回放取证至关重要。

### 2.2 Why——为什么这样设计

#### (1) 为什么用"每秒抽 1 帧"而不是逐帧分析？

监控视频是 25 帧/秒，一小时视频有 9 万帧。但卡车在厂区里行驶，
从进入画面到离开通常需要几十秒——**相邻帧之间的信息高度冗余**。
以 1 秒为间隔采样，信息几乎无损，计算量却降到 1/25。

代码里对应的实现是一个精妙的小技巧（`process_video` 函数）：

```python
ret = cap.grab()          # 只解码定位，不取像素，代价极低
if frame_idx % step == 0:
    ret, frame = cap.retrieve()   # 只有采中的帧才真正解码取图
```

OpenCV 的 `read()` = `grab()` + `retrieve()`。视频解码是 CPU 密集操作，
`grab()` 只推进解码器的游标而不把像素搬运到内存，**跳过的帧只花了
"定位"的钱，省下了"解码 + 拷贝"的钱**。这是视频处理中最经典的
抽帧加速手段。

#### (2) 为什么置信度阈值设 0.5，还要过滤小框？

YOLO 检测结果自带一个 0~1 的置信度分数，表示"模型有多确定这是一个卡车"。

- **阈值 0.5 是精确率与召回率的折中**：调低会漏掉真车（该抓的没抓），
  调高会产生大量误检（把货车车厢、集装箱影子都当卡车）。0.5 是
  COCO 预训练模型的通用经验值。
- **`MIN_CROP_SIZE = 80` 过滤小框是第二道保险**：远处刚出现在地平线的
  卡车在画面里可能只有几十像素宽，裁出来是一团糊。既没有判定价值，
  还会污染素材库。干脆用分辨率下限一票否决。

这两个参数体现了一个朴素的原则：**宁可少存，不可存废图**——
因为下游的 VLM 判定是按张计费的，废图直接浪费推理资源。

#### (3) 为什么要"外扩裁剪框"（CROP_MARGIN）？

检出框是紧贴卡车轮廓的，但下游 VLM 判定需要**理解上下文**：
判断"车斗里装的是什么"时，看到一点地面、车厢边缘，能帮助模型
建立空间关系。所以裁剪时框向四周各扩 10%，并且用 `max(0, ...)` /
`min(w, ...)` 把越界部分裁掉——这是图像处理里处处可见的
**边界钳制（clamping）**手法。

#### (4) 为什么需要"同车去重"？

一辆卡车在画面里停留 30 秒，按每秒一帧的采样会被裁出 30 张几乎
一样的图。这些重复图对下游毫无价值，反而稀释素材库。
代码用一个简单的时间戳变量解决：

```python
if video_time - last_save_time < SAME_TRUCK_SAVE_INTERVAL:
    continue                      # 距上次保存不足5秒，跳过
last_save_time = video_time
```

即：**同一辆车在 5 秒窗口内只存一张**。没有用复杂的跟踪算法
（如 ByteTrack 给每辆车编号），而是利用"车辆停留时间长于采样间隔"
这一业务先验，用一个变量达到目的——**简单方法够用时，不上复杂方法**。

#### (5) 为什么要做增量扫描（`.scanned.json`）？

监控录制是持续进行的，每天都会新增视频。如果每次都从头扫一遍
几十小时的历史视频，是不可接受的浪费。脚本用一个 JSON 文件
记录"每个视频路径 → 上次扫描时的文件大小"：

- 路径和大小都没变 → 跳过；
- 大小变了 → 要么是新文件，要么是**还在录制中的文件**（它的字节
  在持续增长），需要重新扫。

用"文件大小"当指纹是一个粗糙但极其高效的增量判断——比算 MD5 快得多，
且对本场景（文件只增不改）完全够用。

### 2.3 How——完整的执行流程

`main()` 函数的执行流如下：

```
1. 确定扫描目标（命令行参数 > 默认录制目录）
2. collect_videos()：递归收集所有 .mkv/.mp4 等视频，
   并过滤掉 <1MB 的碎片文件（防止把录制半途的残片当正常视频处理）
3. load_scan_record()：读上次扫描记录，比对出"新增/变化"的视频列表
4. YOLO(MODEL_PATH)：模型只加载一次，全程复用（加载要数秒，
   逐视频重复加载是新手最常见的性能陷阱）
5. 逐视频调用 process_video()：
   a. 打开视频，读取 fps 与总帧数
   b. 计算采样步长 step = fps × 1秒
   c. grab/retrieve 循环抽帧
   d. 命中帧送 YOLO predict（指定 classes=[7] 只检出卡车）
   e. 对每个检出框：外扩 → 尺寸过滤 → 时间窗去重 → 裁剪保存
   f. 更新 .scanned.json 记录
6. 汇总统计：扫描了多少视频、检出多少框、实际保存多少张
```

值得注意的一个细节：`predict()` 调用时传了 `classes=[TRUCK_CLASS_ID]`。
COCO 数据集有 80 个类别，ID 7 恰好是 truck。**在推理阶段就做类别过滤**
比检出后再筛更高效——模型的检测头直接跳过其他类别的解码。

## 三、详解 `test_qwen_vl.py`：如何让大模型"看图断案"

### 3.1 What——它在系统中的角色

`test_qwen_vl.py` 是流水线的**第二级：语义判定器**。它把第一级产出
的卡车图片逐张发送给部署在远程服务器上的 **Qwen2.5-VL 视觉语言模型**
（通过 Ollama 推理框架的 HTTP 接口），让模型回答一个传统 CV 很难
回答的问题：

> "这辆车是不是在拖带/装载废旧机动车拆解后的零碎金属零件？"

并把每一张的判定结果（是/否 + 一句话理由）汇总成 CSV 报告。

### 3.2 Why——为什么用 VLM，以及为什么 Prompt 是核心资产

#### (1) 为什么这个任务非 VLM 不可？

"车斗里那堆东西是拆解金属零件，还是轮胎，还是蔬菜？"——这个判定
需要**材质理解**（金属的反光锈迹 vs 橡胶的哑光）、**形状推理**
（不规则碎块 vs 重复圆环）、**常识知识**（什么场景会出现什么货物）。
传统 CV 要为此训练专门的细粒度分类器，需要几千张标注图；
而 VLM 在互联网级数据上预训练过，具备这些常识，**零样本**即可执行任务。

这就是 2023 年以来视觉领域最大的范式转变：**从"为每个任务训练一个模型"
转向"用一个大模型 + 一段提示词解决所有任务"**。

#### (2) 为什么 Prompt 里有那么多"排除条款"？

仔细读代码里的 `PROMPT` 常量，会发现它不是一句简单的提问，而是一份
结构化的"判定规程"：两步判定流程、7 条否定排除项、材质辨别口诀。
这个 Prompt 经历了 v1→v4 四轮迭代，每一版都是被**真实误报**逼出来的：

| 版本迭代 | 被误判为"是"的图片 | 修正手段 |
|---|---|---|
| v2 | 拉的锅碗瓢盆 | 新增"生活废品/日用品"排除项 |
| v2 | 拉的完整汽车 | 强化"完整整车不算零碎零件" |
| v2 | 拉的白色袋装物 | 新增"袋装箱装内容物不可见判否" |
| v3 | 拉的绿色蔬菜 | 新增"农产品/有机物"排除 + 材质辨别要点 |
| v4 | 拉的纯轮胎堆 | "形状重复的圆环" vs "形状各异的碎块" |

这揭示了一个 VLM 时代的重要方法论：**Prompt 就是这个系统的"模型权重"**。
传统 CV 调优靠改参数重训练，VLM 调优靠分析 badcase → 修改 Prompt → 重测。
那些从误报中总结出的排除条款（"轮胎是形状重复的圆环，金属零件堆是
形状各异的碎块"），本质上是在用自然语言向模型注入领域先验。

#### (3) 为什么 temperature 设 0.1？

```python
"options": {"temperature": 0.1, "num_predict": 200}
```

温度控制模型输出的随机性：高温度适合创意写作，低温度适合判定任务。
0.1 意味着模型几乎总是选择概率最高的词——**同一张图判十次，结论一致**。
工业判定场景要的就是这种确定性。`num_predict: 200` 则限制最大输出长度，
防止模型发散写小作文，拖慢判定速度。

#### (4) 为什么要把图片 Base64 编码后塞进 JSON？

Ollama 的多模态接口约定：图片以 Base64 字符串形式内嵌在请求体的
`images` 数组中。Base64 把二进制像素数据转成纯文本，使其能安全地
穿越 JSON 协议。代价是体积膨胀约 33%，但换来协议简单——
一次 HTTP POST 同时携带文字指令和图片证据，无状态、易调试。

#### (5) 为什么要有重试机制和连通性自检？

代码在正式批量判定前先用**第一张图做自检**（`main` 函数）：

```python
test = ask_vlm(images[0])
if test["answer"] == "网络错误":
    print("[!] 无法连接 Ollama，请检查：...")
    return
```

这是典型的 **fail fast（快速失败）** 设计：与其让用户跑半小时后
发现 500 张全部失败，不如第一张就验证链路并把排查指引打印出来。

而 `ask_vlm` 内部的重试循环（最多 3 次，间隔递增 3s/6s/9s）则应对
**瞬时网络抖动**——远程推理服务偶尔超时是常态，自动重试比人工
重跑整个批次省事得多。注意 `except` 子句精准捕获的是网络类异常
（`URLError`/`TimeoutError`/`OSError`），而不是全部异常——
JSON 解析失败这种逻辑问题不应该靠重试掩盖。

#### (6) 为什么要手动"抠 JSON"？

```python
content = content.replace("```json", "").replace("```", "").strip()
start, end = content.find("{"), content.rfind("}")
parsed = json.loads(content[start:end + 1])
```

大模型输出 JSON 时经常"不守规矩"：包一层 Markdown 代码块、
前后加解释文字。这段代码不做任何格式假设，直接找第一个 `{` 和
最后一个 `}` 之间的内容来解析——**对模型输出的容错处理，
是多模态系统工程中最不可或缺的胶水代码**。解析后还校验
`answer` 必须是"是/否"之一，任何格式漂移都会被标记为
"解析失败"而非误判，保证报告的每一行都可信。

### 3.3 How——完整的执行流程

```
1. 收集参数：可选的命令行参数 N 表示只判前 N 张（快速试跑）
2. 扫描 IMAGE_DIR 下所有图片（.jpg/.png 等），排序
3. 连通性自检：用第一张图做一次完整请求，
   失败则打印四条排查指引后终止
4. 打开 CSV 文件（utf-8-sig 编码，保证 Excel 打开中文不乱码），
   写入表头
5. 逐张判定循环：
   a. 图片读为二进制 → Base64 编码
   b. 组装请求：模型名 + Prompt + 图片 + temperature 0.1
   c. POST 到 Ollama /api/chat，带 120 秒超时
   d. 从回复中抠出 JSON，校验 answer 合法性
   e. 失败自动重试（最多 3 次，间隔递增）
   f. 结果写入 CSV 一行：文件名 | 判定 | 模型描述 | 耗时
   g. 终端同步打印进度（带 flush 保证实时可见）
6. 汇总：共判定多少张、其中"是"多少张，报告文件路径
```

CSV 采用 `utf-8-sig`（带 BOM 头）是个贴心细节：不带 BOM 的 UTF-8
CSV 在 Excel 里打开中文全是乱码，加上 BOM 后双击即正常显示——
**结果交付给谁看，就要按谁的工具链优化**。

## 四、给初学者的理论地图

### 4.1 目标检测（YOLO）到底在做什么

YOLO（You Only Look Once）把检测问题转化为**回归问题**：把输入图
划分成网格，每个网格直接预测"这里有没有物体、框在哪、是什么类别、
多大把握"。一次前向推理同时输出所有框——这也是它名字的由来。

理解检测输出只需要抓住三个要素，对应代码里的三个变量：

| 输出 | 代码位置 | 含义 |
|---|---|---|
| 边界框 `xyxy` | `box.xyxy[0]` | 物体位置的左上/右下角像素坐标 |
| 置信度 `conf` | `box.conf[0]` | "这真的是个物体"的把握程度 |
| 类别 `classes` | `classes=[7]` | 物体是什么（7=truck） |

**检测模型只回答"哪里有什么"，不回答"它在做什么"**——这是它和
VLM 的本质分工。

### 4.2 视觉语言模型（VLM）为什么能"看图说话"

Qwen2.5-VL 这类模型由两部分组成：

1. **视觉编码器**（ViT）：把图片切分成小块（patch），编码成一组
   "视觉 token"——可以理解为把图片翻译成模型能读的"外语"；
2. **语言模型**：接收视觉 token 和文字 token 拼接后的序列，
   像续写文章一样生成回答。

所以当你问"车斗里装的是什么"，模型实际在做的是：把图片"读"成
几百个视觉 token，再基于这些视觉信息逐字生成描述。它的"知识"
（什么是金属、什么是轮胎、拆解场长什么样）来自预训练语料，
你的 Prompt 只是在**引导它调用哪些知识、按什么标准下结论**。

这也解释了为什么 Prompt 里写"轮胎是橡胶材质，表面光滑无棱角"
这种看似多余的话有用——它把模型的注意力引向正确的判别特征上，
抑制它跳到"黑色物体 = 废铁"的错误捷径。

### 4.3 抽帧采样的信息论视角

视频是时间轴上的连续信号，帧与帧之间的差异（运动信息）远小于
相似度（静态信息）。按香农采样定理的直觉，只要采样频率高于
"场景变化频率"，信息就基本无损。厂区内车辆移动速度是已知的
（几米/秒），画面宽度对应的物理范围也是已知的（几十米），
由此可推算：**1 秒一帧足以保证车辆不会"瞬移"出画面**。
`video_check.py` 的 `SAMPLE_INTERVAL_SEC = 1` 正是这个计算的结晶。

### 4.4 漏斗式架构的通用性

本文剖析的两级流水线，抽象后是一个可以套用到无数场景的模板：

```
廉价快速的一级检测（YOLO/规则/关键词匹配）
        ↓ 只把"值得深看"的样本往下送
昂贵精确的二级理解（VLM/人工/专家系统）
        ↓ 输出结构化结论
CSV 报告 / 告警推送 / 数据库
```

只要你的场景里"触发判定的对象"在原始数据中占比很低
（监控里的卡车、日志里的异常、邮件里的垃圾），
这个漏斗就能把昂贵的智能推理用在刀刃上。

## 五、总结

| | `video_check.py` | `test_qwen_vl.py` |
|---|---|---|
| **角色** | 目标检测 + 素材采集 | 语义判定 + 报告生成 |
| **核心模型** | YOLO（yolo11n，COCO 预训练） | Qwen2.5-VL（7B，Ollama 部署） |
| **输入** | 视频文件（递归目录） | 卡车 ROI 图片 |
| **核心输出** | 带溯源文件名的裁剪图 | CSV 判定报告（是/否 + 理由） |
| **关键设计** | grab/retrieve 抽帧、增量扫描、时间窗去重 | 结构化 Prompt、低温采样、JSON 容错、重试自检 |
| **体现的原理** | 信息冗余裁剪、检测置信度过滤 | 提示词工程、多模态推理、fail-fast |

这两个脚本合起来演示了现代视觉识别系统的完整思路：
**用成熟的快速模型解决"看"的问题，用大语言模型解决"懂"的问题，
用工程手段（采样、去重、缓存、重试）把两者缝合成可靠的流水线**。
代码中每一处看似朴素的细节——一个置信度阈值、一次 Base64 编码、
一条排除条款——背后都是对识别原理的理解和对真实误报的反思。
读懂它们，你就掌握了搭建同类系统的全部核心要素。
